# T100/V40 — two-process watchdog failure drill (offline, 2026-11-04)

**Scope: simulated account state and local notification receiver only.**
The CI tests create real, isolated OS subprocesses but do NOT read actual
MEXC credentials, access the exchange, submit or cancel an order, contact
Discord, launch Render, change the primary trader, or touch BOXWAVE.

## Purpose

Verify the previous watchdog and sentinel implementations across **actual
process crashes, pauses and restarts**, rather than only mocking calls in
a single Python interpreter. The drill does not measure true exchange
response latency, native stop activation or guaranteed maximum loss.

## Reproduction

From a checkout of branch `codex/t100-readiness-issue-14` on macOS/Linux,
with Python 3.12 available (no trading credentials needed):

```bash
python3 -m unittest -v \
  tests.test_t100_pilot_watchdog_process_failure_drill
```

The file is also included in the T100 explicit pure-Python GitHub Actions
job and full offline test suite. It uses temporary filesystem directories
and deletes them on successful/failed test teardown. **Do not point it at
a real watchdog journal.**

## Scenario A — OS process kill and alert delivery failure

1. Launch a child Python process simulating the *primary* observer's
   healthy FLAT verdict. It uses the actual `PilotWatchdogRunner` with
   SQLite FULL-synchronous journaling and polls repeatedly.
2. Launch a **separate** sentinel process using the actual
   `PilotLivenessSentinel` with a second SQLite journal and a local mock
   notification receiver; assert a recent heartbeat and no alarm.
3. Send actual OS SIGKILL to the primary watcher; it cannot run shutdown
   hooks. Wait beyond the drill-only 1-second stale threshold.
4. Launch a new sentinel subprocess with a *failing* mock notifier.
   Assert `WATCH_HEARTBEAT_STALE`, a latched alert and a pending,
   durably recorded outbox event.
5. Launch a new sentinel subprocess with a *successful* mock notifier.
   Assert the pending event is retried once and marked delivered.
6. Launch the sentinel again; assert no duplicate notification record is
   generated by identical stale observations. Its alarm remains latched.
7. Restart the primary process using the **same** persistent primary
   journal; assert heartbeat freshness returns, while the sentinel's
   historical alert remains latched. Never delete/reset a journal to
   force readiness.

## Scenario B — process alive but frozen

1. Launch the simulated primary and verify repeated healthy ticks.
2. Send SIGSTOP to suspend the running process, without terminating it.
   **PID existence must NOT be interpreted as liveness.**
3. Wait until the stored heartbeat is stale and run the sentinel in a
   separate subprocess. Verify alert and mock delivery.
4. Send SIGCONT and allow fresh heartbeat records. The sentinel can now
   observe a recent heartbeat, but does **not** silently re-arm or erase
   the previous alarm.

SIGSTOP/SIGCONT are POSIX only; the case is skipped on unsupported
platforms. CI runs on Ubuntu.

## Deliberate limitations

- The healthy primary `PilotWatchVerdict` is injected synthetically and
  represents a simulated flat account. No actual MEXC GET was used.
- The notification receiver is a local line-delimited file, **not Discord**.
  The drill tests durable enqueue/ack/retry semantics, not real webhook
  delivery or human acknowledgment.
- A one-second stale threshold is selected only to make the test quick;
  production configuration remains 30 seconds by default. Neither
  value implies an acceptable unprotected exposure period.
- There is no automatic emergency-close method, independently verified
  close fill, cross-margin liquidation proof, process supervisor that
  watches the *sentinel*, or deployment.
- A failure to observe the exchange can indicate network/API outage,
  partial orders or bad permissions; a stale heartbeat cannot itself
  determine whether the account is flat or protected.
- The sentinel can miss failures if its own host/scheduler/disk or
  notification network is down. External supervision and independent
  notification verification remain release blockers.

**Release gates unchanged:** G5 native-stop amendment and actual triggered
execution remain unverified; G6 independent operational emergency close and
live monitored notification delivery remain unverified; G9 four-slot V40
production trial and CROSS-margin safety certification remain blocked.

No change to `entry_allowed=false` or `live_authorization=false`.
